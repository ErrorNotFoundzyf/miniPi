# UpgradePilot 二次开发方案

调研日期：2026-11-04。面向 AI Agent / 大模型应用开发实习。本文是设计方案，未实现、未验证效果；仓库调研基于公开 README、目录及所引文档，并非运行验收。

## 1. 定位与用户

将现有通用 Coding Agent 改造为“Python 项目依赖升级兼容性修复助手”。面向维护 Python 服务的开发者：输入指定版本升级任务或失败的升级 PR，输出候选补丁、独立验证结果和可审查报告。

主要解决版本升级后人工查迁移文档、定位跨文件兼容问题、反复跑测试的工作。研发效能本身就是业务场景；有用户试用和可测结果后，才能进一步声称业务落地。

初版限制：Python + uv + pytest、一个仓库一个升级任务、开发者显式提交任务、仅处理已经批准的版本迁移。Pydantic V1→V2 用作历史回放与原型，不把它等同于当前市场需求；随后用真实仓库待处理的升级任务验证需求。

## 3. 最小用户闭环

1. 用户指定仓库、base commit、目标依赖/版本和受信任的测试配方。
2. 系统在干净环境运行旧版本基线，记录依赖清单、测试集合和失败情况。
3. 按目标版本生成升级候选及 lockfile，复现新增失败。环境安装失败单独分类。
4. 运行适用的规则迁移工具；若已经通过，直接进入验证，无须调用 LLM。
5. Agent 根据失败测试、相关源码及匹配版本的迁移文档修复残余问题。
6. 独立验证器在全新环境验证候选补丁，输出 verified、needs_review、blocked 等状态。
7. 用户查看 Diff、证据和风险；初版导出 patch/report，后续支持显式发布 Draft PR。

示例演示采用两个任务：规则可处理的 Optional 默认值迁移；规则后仍残留的自定义验证或序列化兼容问题。前者展示何时不用 Agent，后者展示 Agent 的实际增量。

## 4. 三个主要技术贡献

### 4.1 版本约束的上下文检索

文档条目包含 package、from_version、to_version、source_url、content_hash。先按版本过滤，再用错误堆栈、符号和关键词检索。首版采用小型人工整理文档集与关键词/BM25；根据检索失败案例再决定是否增加向量检索。

报告串联“失败测试 → 源码位置 → 迁移规则 → 补丁 → 验证执行 ID”。引用文档只能提供依据，不能替代执行验证。

### 4.2 三环境差分验证

| 环境 | 输入 | 用途 |
| --- | --- | --- |
| A | 原始代码 + 旧依赖 | 确认基线与既有失败 |
| B | 原始代码 + 目标依赖及必要清单变更 | 复现升级带来的新增失败 |
| C | 修复代码 + 目标依赖 | 验证原失败消失且未引入可观察回归 |

原始测试及配置由控制面保存，最终验证时使用冻结副本；Agent 新增测试单独计入。测试收集数量下降、skip/xfail 增加、依赖退回旧版或通过 pydantic.v1 绕过原生迁移要求，都不能直接判定成功。合法的依赖、测试或行为变更需进入人工审查。

对于没有测试覆盖的接口，预先固定脱敏请求样本和业务断言，对比状态码、响应字段及序列化结果。旧行为也可能本来有错；业务契约变化必须由维护者确认，不能一律追求复原旧输出。通过测试只代表通过这些检查。

### 4.3 可恢复且有预算的任务执行

外层确定性状态机维护阶段、输入哈希、产物、尝试次数、token 用量及截止时间；内层 Agent 在给定阶段自主定位和修改。建议初版最多三轮修复，每轮固定快照并重新验证。预算耗尽后交付当前补丁和明确失败原因。

阶段产物落盘后才能转移状态；恢复时校验 commit、目标版本和产物哈希。相同请求以仓库、commit、版本和配方哈希去重；发布动作单独记录，避免重复创建 PR。单机 SQLite + 独立 worker 足够，不提前引入分布式基础设施。

### 必须注意的现有实现

`HookRegistry.emit()` 在首个非 None 结果时短路，且回调异常后记录日志并继续执行。它适合现有通用扩展语义，不能直接充当服务模式的强制安全边界：一个中性的 HookResult 也可能使后续策略不执行。

业务服务在工具执行器和发布器上设置不可绕过、异常即拒绝的策略；按需新增明确的策略聚合接口并测试，避免全局改变已有 Hook 行为。文件锁只能解决并发写，不能替代任务级工作区隔离。

每个任务使用隔离容器和独立工作副本；模型密钥留在控制面，执行容器不挂载宿主凭据或 Docker socket。环境准备与修复执行分开，按阶段限制网络、资源和超时。独立验证环境从干净基线应用获准补丁，评测保留测试不放入 Agent 工作区。容器是约束的一部分，不宣称绝对安全。

## 6. 评测设计

先做 5 个探索案例，确认确有规则工具不能解决、且能独立验证的问题，再扩展到约 20–30 个案例。区分人工构造和真实开源历史任务；按仓库/迁移类型划分开发集和保留集，避免同模板泄漏。

比较：仅升级版本；规则工具；原始 my-pi-agent + 明确迁移提示；UpgradePilot。可增加 mini-swe-agent 基线。涉及 LLM 时固定模型快照、任务输入、工具权限和预算；共同使用同一独立验证器。工具成本与预处理成本一并统计。

主要指标：独立验证通过数/总任务数、错误标记成功数/标记成功数、每个任务及每个成功任务的 token/费用、耗时、人工审查分钟数。超时、环境失败、拒绝处理和未完成任务都记录，不从结果中静默移除。小样本报告原始计数，避免夸大百分比。

消融仅保留两项：移除版本文档检索；移除差分门禁。分别观察修复通过率及错误标记成功率。对随机性较大的结果至少重复部分任务，保存每次轨迹；所有指标以实际运行结果填写。

## 7. 六周实施顺序

按个人每周约 20 小时估算，现有代码熟悉程度会影响工期。

1. 第 1 周：读懂并跑通原项目；准备五个案例和规则工具基线。交付可重现输入与验收配方。
2. 第 2 周：CLI、隔离执行器、A/B/C 环境和报告。先跑通不用 LLM 的完整链路。
3. 第 3 周：接入 Agent、版本文档检索、三轮预算。交付规则后残余问题的修复演示。
4. 第 4 周：冻结验证、异常分类、检查点恢复；测试伪成功和中断恢复。
5. 第 5 周：简单任务页面；时间允许才接升级 PR 导入和 Draft PR 发布。
6. 第 6 周：扩展与冻结保留集、运行基线和消融、整理失败案例和演示录像。

前两周若案例几乎都被规则工具解决，应调整案例/升级类型；若通用 Agent 表现相当，则将贡献如实定位为验证、任务编排与审查效率，而非模型修复能力提升。

## 9. 学习过程中新增的框架优化候选

记录日期：2026-11-11。以下来自 Skill 章节讨论，是后续魔改时再设计的框架改进方向；尚未实现，不代表已经纳入上述 UpgradePilot 初版范围。

### 9.1 补齐技能自动选择与正文加载闭环

已落地 `load_skill(name)`。启动时提供技能清单，模型调用后把正文作为工具结果送入下一轮。用户可继续通过斜杠命令显式调用。作用域、重载和验收见 10.2。

关联代码：`src/my_agent_core/skills.py`、`src/my_agent_core/agent.py`、`src/my_coding_agent/macro.py`。

### 9.2 新增 Create Skill 机制

用户提出：后续增加创建技能的能力，而不只是发现和使用已有技能。

候选流程：根据用户需求或可复用任务经验，生成技能草稿（name、description、正文）→ 校验格式和命名 → 写入约定目录的 `SKILL.md` → 重新发现技能并更新可用清单。

具体入口尚待决定，可以是命令、工具或交互流程。自动从经验提炼是可选方向，不视为已授权现在自动生成或安装技能。

后续需要明确：保存到项目还是用户目录、同名冲突处理、创建与更新的区别、何时重载 Manager 和 system 清单，以及如何用实际任务验证技能是否有用。避免仅生成文件但当前 Agent 无法发现或使用。

### 9.3 多 Agent 并发与依赖调度

记录日期：2026-11-12。用户确认记录，待后续优化；本节是候选设计，尚未实现，不改变现有调度行为。

**当前基线**：内置 `task` 工具的 `is_parallel_safe=False`，`ToolRegistry.execute_batch()` 遇到它会使整批工具调用串行。`start_task()` 等待子代理完成后返回。异步接口可以由调用方显式用 `asyncio.gather` 组织并发，但内置委派路径不会自动这样运行；异步等待也不等于整个后端服务阻塞。

**目标与依赖语义**：独立子任务允许并发，有结果依赖的任务分步执行。例如“审查代码 + 查阅文档”可以并发；“分析问题 → 根据分析结果修改代码”需要父 Agent 收到分析结果，再生成修改任务。仅将两个预先生成的任务串行执行，不会自动把前者结果注入后者。首版采用父 Agent 分轮委派，后续再评估显式依赖图。

**按具体调用决定调度**：不要只把 `task` 的全局标记改成 `True`。考虑扩展工具调度接口，按本次参数、子代理权限与执行环境决定是否并发。只读审查、检索类子代理优先开放并发；共享工作区中的修改型子代理默认串行；任意 Bash 能力默认保守处理。只读资格应由实际工具权限约束，不能只看代理名称或提示词声明。

**共享资源与隔离**：独立 Session 隔离对话记录，并不隔离 LLM 对象、复用工具和工作目录。复用现有文件级锁保护单次修改，但它不能解决“两个代理分别想把同一配置改成不同值”的意图冲突。后续考虑为修改型子代理分配独立 Git worktree，由父 Agent 审查和合并改动；worktree 也不自动隔离外部服务等资源。

**并发额度与取消**：通过共享并发额度限制同时运行的子代理数量，并明确嵌套委派的额度归属，避免无界扩张或父任务占额度等待子任务导致死锁。父任务取消时，停止启动排队任务，向运行中的子代理传递取消信号，取消对应 asyncio Task，并清理工具进程。取消不撤销已完成的文件修改。

**进度与结果**：按任务 ID 关联排队、运行、成功、失败和取消状态，结果携带摘要与 Session 路径。独立收集每个子任务的结果，明确单个失败是否取消其他任务；首版优先保留其他任务的成功结果，由父 Agent 决定重试或继续。事件名称与 RPC/TUI 展示契约在实现时设计。

实施顺序：

1. 首版：只读子代理并发、修改型串行、最大并发数、父子取消传播、独立结果收集及任务状态事件。
2. 第二阶段：修改型子代理 worktree 隔离、变更审查与冲突合并。
3. 后续按需求：显式任务依赖调度与嵌套任务预算。

验收覆盖：独立任务确实重叠运行；依赖任务获得前序结果后才启动；权限不足以证明只读时保持保守调度；并发上限生效；单任务失败时其他结果可追踪；取消后排队任务不启动、运行任务和工具资源被清理。性能收益以实测为准，不承诺任务数倍加速。

关联代码：`src/my_agent_core/tools/builtin/task.py`、`src/my_agent_core/registry.py`、`src/my_agent_core/subagent_tasks.py`、`src/my_coding_agent/mutation_queue.py`；事件、RPC 与 TUI 的具体改动位置在实施前追踪确认。

### 9.4 Loop 微内核的运行边界与事件一致性

记录日期：2026-11-15。用户确认记录，待后续优化；以下为候选方案，尚未实现或验证，不改变现有 Loop 行为，也不自动纳入 UpgradePilot 初版范围。

保留现有职责拆分：Agent 负责装配、Session 与订阅通知；run_agent_loop() 负责轮次推进和结束判断；_assistant_turn() 负责模型事件转换及重试；_execute_tools_turn() 负责工具批次处理。优先完善执行边界，再评估性能优化。

#### 9.4.1 增加运行上限（第一批）

当前内层以 has_more_tools 或 pending_messages 决定继续，iteration 只计数，没有通用最大轮次检查。MAX_LENGTH_CONTINUATIONS=3 仅限制特定输出截断续写分支，不能限制正常工具循环。

候选：增加可配置的最大轮次、总运行时间及工具调用次数，例如 max_turns=30、max_duration_seconds=600、max_tool_calls=100；这些名称和数值仅作设计示例。明确额度是否跨 follow-up 累计，以及模型重试、压缩请求是否计入时间与费用预算。轮次限制不能替代时间限制；正在等待的操作还需要超时和取消传播。

达到上限时保留已完成消息和结果，以明确的停止原因结束，不标记为任务成功。停止原因的事件、run() 返回行为及 RPC/TUI 契约需要同步设计。

#### 9.4.2 消息提交先于完成事件（第一批）

已实现。助手终态与工具结果先追加到内存历史再发 `MessageEnd`。产品层 Agent 仍在通知订阅者前保存 Session，保存异常沿原路径返回。

当前 assistant 和正常 tool 结果路径先 yield MessageEnd，再于生成器恢复后追加到 messages；外层 Agent 可能已经保存 Session 并通知订阅者。正常持续消费后会补齐，但订阅者当下读取内存历史，或消费者在此停止时，可能观察到不同状态。

候选：统一规则为“完整消息先更新内存，再广播 MessageEnd”，随后由 Agent 持久化并通知外层。一起调整现有追加位置，保证每条消息只追加一次；覆盖用户、assistant、工具、合成中断结果与自动续写消息的路径。

这不是内存与磁盘的原子事务，仍须明确 Session 写入失败的处理。目标是让收到完成事件时，对应内存消息已经存在。

#### 9.4.3 明确关闭链并等待取消完成（第一批）

本轮已实现主对话模型流、上下文压缩请求和上层事件迭代器的关闭链，并在并发工具批次异常退出时等待子任务收敛。

当前工具子生成器的 finally 会取消并等待 runner，但多层 async for 提前退出并不自动等于内部所有生成器和任务已立即清理。需区分 agent.abort() 的协作取消、asyncio Task.cancel()、显式 aclose() 和消费者 break。

候选：明确“调用方 → Agent 事件流 → Loop → 当前模型流或工具子生成器 → 后台任务”的关闭责任，必要时使用显式关闭或异步上下文管理。ToolRegistry.execute_batch() 异常路径当前会取消未完成的并发任务，可补充等待这些任务退出，再传播原异常，避免遗留未收敛任务。

关闭优先保证资源清理；不要在生成器关闭的 finally 中强行 yield AgentEnd。正常结束事件与强制关闭时的状态通知分别设计。中断工具调用的结果配对、Session 恢复与已完成文件修改保留策略也需保持一致；取消不等于回滚。

#### 9.4.4 补齐取消检查点与信号传递（第二批）

候选检查点：每轮开始、上下文准备完成后、模型前 Hook 完成后、实际请求模型之前，以及工具审批完成后到实际执行之前。避免取消已经发生，却继续启动下一项工作。

追踪 ContextManager 压缩内部的模型请求是否接收取消信号；只在外层检查，不能停止已经开始的内部等待。保留 steering 在轮次边界注入的语义，不把 steering 当成取消或立即抢占执行。

#### 9.4.5 限制进度积压与慢订阅影响（第二批）

当前工具进度使用无容量上限的 asyncio.Queue；Agent._notify() 按顺序执行并等待订阅者。工具持续输出而消费者或订阅者较慢时，进度队列可能积压，订阅者也会拖慢主事件流。

候选：为进度设计容量和合并策略。百分比、状态快照可保留较新值；文本增量应合并成块或转存日志，不能任意丢弃；最终结果和消息完成事件须完整处理。不能只给 Queue 添加 maxsize：现有 put_nowait() 及工作线程投递路径还需要处理满队列，结束哨兵也必须可靠送达。

可选增加后台订阅模式，但须明确事件顺序、队列容量、异常记录、取消和关闭时的排空策略；保留需要同步完成的处理路径，避免简单地把所有监听器变成后台任务。

#### 9.4.6 修正命名、注释与工具状态语义

has_more_tools 同时用于工具后续轮次和输出截断续写，可考虑改成 needs_another_turn 等符合实际含义的名称。Registry 的并发依据是 is_parallel_safe，不是是否只读；修正“含写必串行”等旧注释，避免误导。

ToolExecutionStart 当前在审批前发出，应明确它表示进入调用处理流程；如增加等待审批、实际运行等状态，需要同步事件和界面契约，避免把等待审批显示为正在执行。

#### 实施顺序与验收

| 优先级 | 内容 | 主要目标 |
| --- | --- | --- |
| 第一批 | 运行上限、完成事件前提交消息、关闭链与取消收敛 | 防止失控运行，保证状态与资源一致 |
| 第二批 | 取消检查与信号传播、进度容量与合并 | 减少取消延迟和内存积压 |
| 随实施整理 | 命名、旧注释、工具状态语义 | 提高可读性，减少界面误判 |

使用假的模型和工具验证实际边界行为：

- 模型持续请求工具时，在配置上限停止，并保留明确原因和已完成结果；模型内部重试不会绕过总时间预算。
- 订阅者收到 MessageEnd 时可读取对应内存消息；在该事件后立即停止消费，不造成重复追加或消息遗漏。
- 工具执行中取消、关闭多层事件流、外层提前退出后，相关任务被明确关闭和等待，工具资源完成清理。
- Hook 或上下文准备等待期间取消后，不再启动新的模型请求或工具；压缩内部请求的取消可追踪。
- 工具大量输出且消费者缓慢时，缓存受控；文本顺序和最终结果完整，结束标记不丢失。
- 正常的工具续轮、steering 优先于 follow-up 的检查顺序、重试和截断恢复行为不回归。

### 9.5 Memory 系统：可靠写入、历史召回与受控学习

记录日期：2026-11-15。用户确认记录，待后续优化；本节依据当前工作区与当日读取的 Hermes 官方 main 分支文档、源码整理。以下均为候选设计，尚未实现或验证，不自动纳入 UpgradePilot 初版范围。Hermes main 持续变化，实施前应固定参考 commit 并重新核对接口；不能直接照搬教程中的历史版本或效果数字。

**当前基线与保留边界**：本项目已有 MEMORY.md / USER.md、字符预算、条目分隔、启动时冻结快照、memory 工具及临时文件原子替换。CodingAgent 包装一个核心 Agent，由内部 Agent 创建 MemoryStore，不是两层分别运行两套记忆。运行中的 add/replace/remove 更新最新条目和文件，不自动刷新快照及 system；新 Agent 加载同一目录，或显式 reset 后重新拼装 system，才在正常路径下采用新版本。产品 /new 当前创建新 Agent，并不调用旧 Agent.reset()；reset 会清空当前 Session，不能用于仅刷新记忆。子代理默认禁用长期 Memory，并过滤父级 memory 工具。

冻结快照也被 Hermes 保留，本身不是待淘汰机制。优化重点是围绕它完善写入、捕获、召回和用户控制；保持前缀稳定只增加缓存复用机会，不保证缓存命中率。Session 保存过程、messages 承载内存对话、Context 准备本轮视图、Memory 保存精选长期信息，四者不能混用。

#### 9.5.1 结构化结果与写入失败保护（优先）

已实现。读取允许文件缺失，读失败时返回诊断并禁止修改对应文件。增删改先原子替换文件，再提交内存条目。工具返回提交、无变化或失败状态及对应错误类别。新写入的内容会规范换行并拒绝独立的条目分隔符，手工导入的超长文件仍可读取及删除条目。

当前 MemoryStore 的超限、歧义、未找到等分支返回字符串，通用 Tool 层可能将其包装为 ok=True；“函数正常返回”与“记忆操作已提交”没有明确区分。候选：统一操作结果，包含 success、错误类别、message、容量用量，失败时按需返回当前或相近条目；区分成功、拒绝、无变化和待审批，不将待审批当作落盘成功。字段和 ToolResult 映射在实现时确定，避免界面、模型和上层代码各自解析文字。

改造前，读取异常会被当作空文件，增删改也会先更新内存再落盘。现有实现把磁盘文件作为更新的来源，读取或写入出错时返回失败，并保留会话已加载的快照。

字符上限目前主要约束 add/replace；需要明确手工导入超长文件、包含条目分隔符的内容、换行和编码的处理规则，不能声称所有加载入口都已有硬限制。保留原子替换，但不把它等同于事务、并发隔离或任意断电情况下的绝对持久性。

#### 9.5.2 新增局部 patch，减少整条替换导致的信息损失

已实现 `memory(action="patch")`。唯一命中时只修改对应片段，条目内重复命中和跨条目重复命中都返回歧义。原有 `replace` 仍用于整条替换。

当前 replace 以 old_text 定位条目，再用 new_content 替换整条。模型若把它当作局部替换，可能抹掉同条中的其他事实。Hermes 当前向模型提供 add/patch/remove，不再提供 replace action；其内部仍有兼容旧暂存操作的代码，不能据此说整个存储类已删除 replace 方法。

候选：增加 patch，只替换目标条目中的指定片段，其余内容保留。验证跨条目和条目内多次匹配的歧义，明确整条精确匹配优先级；继续提供整条重写时，应使用含义清楚的接口，或要求 old_text 指定整条内容。设计旧工具调用、历史记录和旧客户端的兼容反馈，不静默改变旧 replace 的语义。

示例：原文“用户偏好中文、源码位置和完整调用链”，将“中文”改成“双语”后，其他两项仍保留。唯一子串匹配只是定位保护，不代表内容正确，也不是语义去重。

#### 9.5.3 文件锁、写前重读与原子批量操作

已实现单文件锁、锁内重读及 `memory(action="batch")`。批量操作按最终内容检查容量，成功后一次保存。

改造前，多个 Store 指向同一目录时可能基于各自的旧副本写入。当前文件锁覆盖同一目标的读取、校验与保存。锁允许等待到配置的超时时间，超时返回可重试错误。

增加同一 target 下的 operations 批量接口：在工作副本上执行全部操作，按最终结果检查字符预算，全部通过才一次提交；任何操作失败不提交整组变化。这样可以一次移除过时条目并新增重要信息，避免“先删成功，后加失败”的中间状态。首版不承诺跨 MEMORY.md 与 USER.md 的多文件事务。

锁解决数据覆盖，不解决两个 Agent 对同一事实作出相反判断的语义冲突。保留按用户、项目或 profile 选择目录的明确边界；当前 CodingAgent 的项目/全局目录是择一使用，不是自动合并。多 Agent 不应仅因存在文件锁就默认共享同一记忆库。

#### 9.5.4 用户可查看、可纠正的记忆管理

候选：提供查看当前文件状态、提示词快照版本、容量，以及编辑和删除的产品入口，让用户能区分“模型说已记住”“操作已落盘”和“当前 system 已采用”。记录必要的修改前后内容、操作来源和会话关联，明确保存期限与敏感信息处理；不默认把全部对话复制进记忆审计记录。

可选写入审批和暂存区，覆盖新增、修改、删除。批准时核对目标条目是否仍与审核版本一致，已改变则拒绝或要求重新审查，避免旧关键词命中新条目。待批准操作不能提示为保存完成。后台修改和前台操作是否采用不同默认策略，在实施时设计。

增加针对持久化提示词内容的检查，识别已知注入、凭据外传及不可见字符等风险；来源、适用范围和用户明确纠正优先于模型推断。检查不能保证事实正确或绝对安全，工具审批也不能代替通用文件工具的访问控制。删除条目不自动删除旧 Session、当前快照或其他副本，应在界面准确解释范围。

不使用 Agent.reset() 作为单纯“刷新记忆”的按钮。若需要保留当前对话的显式刷新，单独设计重载 Store、重建 system、处理旧快照与新事实冲突及缓存变化的行为，并验证无需清空 Session。

#### 9.5.5 增加 session_search，补齐未精选历史的召回

当前 Session 文件存在，不等于模型拥有跨 Session 检索能力。候选：为获准的历史会话建立索引，先采用本地 SQLite FTS5 等全文检索，让模型按需搜索和浏览历史消息；精选 Memory 继续保持小容量、随启动提供。

结果包含可追踪的 session_id、消息或 entry 标识、时间和匹配内容，支持展开相邻消息。索引是派生数据，Session 仍为记录来源；明确新消息增量索引、删除/重置、分支与 rewind 的可见性和重建方式。限制可检索的用户与项目范围，控制结果数量和输入预算，引用历史不等于将旧指令提升为当前指令。

FTS5 是全文检索，不称为向量语义搜索。先测关键词召回不足的案例，再决定是否增加向量或混合检索；检索结果整理是否调用 LLM 也需单独计成本。

#### 9.5.6 有预算的记忆提醒与后台复盘

当前主要依赖模型主动调用 memory；普通回答“已记住”不会写文件，工具描述也尚无完整保存规则。先补齐简洁清楚的保存、跳过和纠错指引，再评估周期提醒及后台提炼。

候选：在受控时机回看交互，提取稳定偏好、跨任务事实或有适用范围的经验；任务进度交给 Session/任务看板，多步骤方法交给 Skill。与 9.2 Create Skill 候选协同，避免同一经验无差别塞入所有提示词。对模型推断、重复偏好和用户纠正进行区分，不能保证自动提取一定准确。

后台复盘可使用受限制的模型与工具，配置启停、频率、输入和调用预算、超时及取消策略。产生候选或写入文件后通知用户；操作成功才计为完成，复盘被取消、失败或待审批时状态可追踪。避免抢占前台任务，也防止旧快照产生的后台修改覆盖用户刚提交的纠正。

后台写入与冻结快照可以共存：仅修改文件，不自动重写当前 system。压缩前或会话结束处理是可设计的触发点，不预设每个 Hook 都必须启动额外模型。收益要同时测捕获率、误记率、重复率和额外 token/费用，不能只统计写入条数。

#### 9.5.7 外部 Memory Provider（后续按需求）

当前没有专门的外部记忆提供商接口。仅在本地精选文件和历史检索无法满足需求时，再考虑可插拔提供商：按需召回、轮次同步、会话结束/压缩前处理及专用工具，保持核心层接口与具体 SDK 依赖分离。

明确本地 Store 与外部数据的来源、覆盖范围、删除和同步语义；外部召回使用独立的动态输入位置或受控消息，不无条件重写冻结 system。同步前处理凭据和敏感信息，配置额度、超时、失败降级、取消和关闭时的待写入处理。外部服务失败时本地基础记忆可用，不预先承诺单例、跨设备一致性或必须引入向量数据库。

记录日期：2026-11-16。用户确认记录，待后续优化；以下依据当前工作区源码与本章讨论整理，均为候选设计，尚未实现或验证，不改变现有运行行为，也不自动纳入 UpgradePilot 初版范围。与 9.3 子代理调度、9.4 Loop 关闭及预算共用设计边界；此处 Background 指命令子进程，与 9.5 的后台记忆复盘不同。

**当前基线**：TaskItem 是待办卡片，TaskStore 将当前状态保存到工作区 .my_agent_core/tasks.json；BackgroundJob 是一次后台命令的运行记录，process 关联操作系统子进程，task 是调度 _worker 协程的 asyncio.Task，两者不是同一种对象。模型通过 bash(run_in_background=True) 选择后台路径，程序也可直接调用 run_process()。后台启动确认先作为工具结果返回；_worker 等待进程并收集输出，结束后将通知加入 follow-up。内层循环收尾时，外层才读取已到达的通知；入队不会自动重启已经返回的 run()。

#### 9.6.1 统一待办校验与失败提交保护（第一批）

已实现。单条与批量共用候选状态校验。校验和落盘成功后才提交内存状态及编号。新版保存 `dependencies`，从中派生当前 `blocked_by`；旧文件仍能加载。并发实例提交前会比较磁盘版本，过期更新会刷新看板并要求重试。

目标：不只在工具描述中要求遵守依赖，而是在数据层拒绝不合法的状态更新。先在候选状态副本中应用本次字段、增删依赖，再检查最终结果：标题及状态合法、依赖存在、无自依赖及环、进入或保持 in_progress 时没有未解决依赖、单进行中约束符合配置。批量 write 与单项 create/update 复用同一校验和解锁规则，防止换入口绕过。

前置任务完成后仍保留依赖边。重开已完成任务时，待办下游重新显示阻塞，进行中的下游需要先退出进行中状态。删除仍被活跃卡片引用的前置任务前，需要解除引用。旧版已移除的依赖边无法从现有文件恢复。解锁表示卡片具备开始条件。

整次变更校验通过后再提交；校验或落盘失败时保持原内存、磁盘状态及编号分配语义可解释。批量部分失败不留下半组修改。保留原子文件替换，但共享文件需按实际多实例需求设计锁内重读与提交，不能把单次工具批次串行视为跨 Agent、跨进程互斥。

明确 write 是批量更新/新增还是全量替换；首版优先保留现有行为并修正说明，如需替换增加显式语义和兼容处理。TaskStore 校验只约束卡片状态；模型仍可直接执行 edit/bash，不能据此宣称真实执行已经受依赖图控制。

#### 9.6.2 补齐后台作业查询、等待与取消（第一批）

候选接口示例：job_status(job_id)、job_logs(job_id)、job_wait(job_id, timeout)、job_cancel(job_id)；这些名称尚待设计，当前未提供。结果统一包含作业 ID、运行状态、退出码、结果位置及明确的未完成/失败原因。区分已登记、启动中、实际运行与终态，避免返回编号就声称进程已成功启动。

显式等待解决本章核心场景：测试在后台运行时先做独立工作；开始依赖测试结果的修复前，调用等待接口取得结果，再让模型生成后续工具参数。异步等待不阻塞整个后端服务，但当前 Agent 推理链会等待。等待超时返回仍在运行等明确状态，默认不等于取消命令；未知 ID、已完成、失败和已取消均有确定反馈，避免让模型反复执行 Bash 轮询。

补充工具指引：下一步立即依赖命令结果时优先前台等待；有可独立推进的工作时才考虑后台。前后台选择仍可由模型或调用方作出，框架不自动理解任意自然语言和命令之间的依赖。进程退出码为 0 只代表命令正常退出，不自动证明业务需求完成。

#### 9.6.3 安全点消费通知与空闲唤醒（第二批）

保持模型生成及工具执行期间不被通知粗暴抢占。先沿用 follow-up 安全点，并明确运行中何时处理、长工具循环是否延迟过久及如何受预算限制；若引入更早的通知消费点，需显式设计优先级，避免悄悄改变 steering/follow-up 契约。

为长期运行的产品服务增加单一 prompt 调度入口：有活跃运行时只排队；空闲时按配置启动通知处理。处理“检查队列为空 → 当前运行结束 → 后台通知恰好到达”的竞态，保证后续处理被安排且不会同时启动两个 prompt。任务完成回调只交付结果，由调度入口决定启动，避免后台 worker 递归调用 Agent.run()。

为通知设置唯一标识、所属 Agent/Session 和处理状态；等待接口已取得结果后，后续通知应能识别重复，不重复自动更新任务或触发同一动作。明确 abort、清队列、切换会话、关闭服务后的结果归属，旧作业不注入新会话，用户取消后不自动重新唤醒模型。唤醒遵守 9.4 的轮次、时间和调用预算，并提供关闭自动接续的选项。

一次性的 asyncio.run() 结束会关闭事件循环；后台继续运行和自动接续需要明确的常驻服务生命周期，不能仅靠入队或 atexit 实现。

#### 9.6.4 可选的卡片与作业关联、依赖执行（后续）

先提供可追踪的 task_id 与 job_id 关联，让用户和模型看出“这张待办对应哪次测试”。一张卡片可能关联多个作业或重试，需区分当前尝试和旧结果，旧尝试通知不能覆盖新状态。命令失败保留日志和失败原因，不把“进程结束”自动映射为“卡片完成”。首版由模型或明确的业务验证规则决定卡片更新。

在查询、等待与通知可靠后，再评估显式工作流：执行节点声明依赖和前序输出，调度器只启动条件满足的节点；有结果依赖的下一步在结果可用后生成参数，不能把两条预先生成的命令串行执行称为自动传递结果。明确失败、取消、重试、跳过和依赖完成的规则，与 9.3 共用依赖模型。不要尝试从任意 Bash 字符串或卡片标题推断可靠依赖。

示例目标：A 运行测试，C 整理更新说明可与 A 重叠；B 根据报错修复必须先取得 A 的真实结果。卡片状态校验、真实执行调度和共享文件访问是不同问题，需分别约束。测试读取工作区时并行修改相同文件可能使结果失真，可采用冻结副本或工作区快照验证，并记录执行对应的代码版本。

#### 9.6.5 输出、资源与生命周期管理（第一至第二批）

当前 communicate() 收集完整输出后才截取前 20000 字符，不能限制收集阶段内存，也不提供实时尾部日志。候选：持续读取 stdout/stderr，按容量写日志文件并保留有界摘要，支持分页/尾部读取和截断提示；两条输出流需要同时排空，避免管道堵塞。完成通知只带紧凑摘要和结果引用，长日志按需取用，避免大量结果挤占上下文。

后台分支目前未使用 bash 的 timeout，也没有复用普通分支的 Shell 选择。统一前后台 Shell、环境、工作目录与超时语义，覆盖 Windows Git Bash/默认 Shell 和 POSIX。增加作业数量、并发数、总时长及日志保留额度；排队启动前再检查取消，避免无限派生子进程。

与 9.4 关闭链协同增加显式异步 close：处理启动中取消、运行中取消、超时及已结束竞态，终止进程/进程组并等待 worker 和子进程收敛，再完成关闭。atexit 仅作兜底，不能承诺断电或强制终止时执行；Unix 进程组和 Windows 进程树清理也不能代替完整执行隔离。

后续按需求持久化作业元数据、日志路径与通知处理状态，重启时把无法确认的作业标记为中断或待核实，不凭旧 PID 重连并杀进程。自动恢复实际执行需要专门的 worker/进程管理方案；首版可只恢复结果查询与未处理通知。定义完成记录淘汰和日志清理规则，避免 jobs 字典无限增长。

### 10.2 FC-01：增加模型可调用的 load_skill

**FirstCoder 机制**：[create_load_skill_tool()](../../FirstCoder/firstcoder/tools/load_skill.py) 从已解析的技能目录按名称查询，调用 `SkillLoader.load()` 获取正文，追加 `skill_selected`、`skill_loaded` 记录，返回包含正文、内容哈希等信息的普通 ToolResult。选择理由记录为 `model_tool_call`，不是框架自行猜测技能。

**本项目实现**通过 [SkillManager](../src/my_agent_core/skills.py)、[Agent 工具装配](../src/my_agent_core/agent.py) 和 [加载工具工厂](../src/my_agent_core/tools/builtin/load_skill.py) 接入。显式入口仍可用 `invoke_skill()` 和 `/skill:name`。

1. 系统提示词列出可自动调用的技能名称、描述和调用指引。只有存在可自动调用的技能时才装配内置 `load_skill`。
2. `load_skill(name)` 按精确名称取得已发现的正文，封装为 `role=tool` 消息。名称不在允许范围内或正文超过工具消息上限时返回错误。
3. 工具调用与正文随现有工具事件及会话消息记录。重复取用读取当前目录快照，`/reload` 刷新快照及加载入口。
4. `disable-model-invocation: true` 保留手动入口。子代理的独立加载器同时受其技能名单和工具名单约束。

目标调用链：`技能清单 → 模型选择 → load_skill → 正文工具消息 → 模型按正文继续`。

验收：假模型先选择技能再执行技能要求；未知技能为失败结果；无技能时行为明确；显式调用继续可用；不会一次注入全部正文或递归启动 Agent。涉及工具描述与默认提示词装配的回归一并检查。

### 10.3 FC-02：TaskStore 依赖硬校验、失败零提交与可选版本控制

**FirstCoder 机制**：[validate_plan()](../../FirstCoder/firstcoder/planning/validation.py) 检查依赖存在、无自依赖及环、linear 单进行中、所有进行中任务的上游已完成；[reducers](../../FirstCoder/firstcoder/planning/reducer.py) 先构造候选计划，校验后返回；[TaskPlanService](../../FirstCoder/firstcoder/planning/service.py) 在锁内重放最新状态，以 `expected_revision` 检查旧版本更新，再追加提交记录。

**本项目接入位置**：[TaskStore](../src/my_agent_core/task_store.py)、[todo 工具](../src/my_agent_core/tools/builtin/task_tools.py)。沿用现有看板文件和工具协议，先修约束，不先移植完整 planning 包或自动 DAG 调度器。

第一阶段：

1. 为 `create()`、`update()`、`batch_write()` 提供共享的候选状态校验。先在副本应用全部字段和依赖修改，再检查最终结果。
2. 上游未完成时禁止进入或保持 `in_progress`；保留配置决定的单进行中约束。批量入口不能绕过。
3. 校验全部成功后写盘，落盘成功后发布新内存状态，或使用可验证的回滚方式；编号分配、解锁列表同样不能留下半次提交。
4. 明确 `write` 当前的更新/新增语义，不静默改成全量替换。完成后移除依赖边的现状、删除前置任务、重新打开已完成任务应有明确规则；若支持重新阻塞，需另外保留依赖事实，不能依靠已删掉的边恢复。

第二阶段，在后台作业会更新看板前增加 revision、锁和写前重读。跨进程场景必须在锁内读取最新磁盘状态；只锁旧内存对象或最后的文件替换仍可能丢更新。先保留旧调用的兼容路径，再设计 `expected_revision` 参数。

验收：A 未完成时 B 不可开工；同次修改状态与依赖按最终结果判断；多项修改中最后一项非法时整组零提交；磁盘故障后内存保持已提交状态；两个更新基于旧 revision 时后者收到明确冲突。

范围限制：TaskStore 只能约束卡片，不能阻止模型绕过看板直接调用 Bash/edit。真实执行依赖是另一项调度能力，与第 9.6 节区分。

### 10.4 FC-03：摘要先生成候选、验证，再提交；失败有界退避

**FirstCoder 机制**：[ContextWindowManager._generate_validate_commit()](../../FirstCoder/firstcoder/context/manager.py) 调用 `generate_candidate()`，以候选 checkpoint 重建视图、校验工具消息序列与预算，合格后才 `commit_candidate()`；[LlmCompactService](../../FirstCoder/firstcoder/context/llm_compact.py) 校验摘要边界和未消费工具事务。管理器还检查自动压缩熔断与无收益输入指纹。

**本项目接入位置**：[ContextManager._summarize_from_cut()、force_compact()](../src/my_agent_core/context.py)。继续让 ContextManager 只算视图，由现有 ContextSessionBridge 将成功的 pending_compaction 写入 CompactionEntry。

实施步骤：

1. 摘要、cut、retained_tail、候选视图先存局部变量；验证前不改 `_summary` 等有效缓存。
2. 检查非空、切点合法、assistant/tool 配对、压缩收益、目标容量；内容非空不等于压缩成功。语义是否完整仍需真实任务验证，结构校验不保证事实无损。
3. 验证通过后再更新缓存、记录视图和生成 pending_compaction；失败不写成功的缓存 entry。手动压缩失败应保留原有效缓存，避免 `force_compact()` 提前清空旧成果。
4. 保留最近工具结果及其调用配对。后续需要更精细保护时，记录是否已进入一次成功的模型请求；不能把“工具刚执行完”当成“模型已消费”。
5. 为相同输入记录失败/无收益指纹和有限冷却，成功或明确手动重试时重置。模型重试、压缩重试分别计数和计费，防止反复摘要。
6. 原视图超过实际可接收容量、候选又失败时，返回可见的压缩失败及恢复建议；不继续无条件发送相同超限输入。区分软触发阈值与硬容量。

验收：空摘要、超长摘要、错误配对、请求异常都不覆盖旧缓存或追加成功 entry；有效候选可经 Bridge 落盘并重启恢复；同一无收益输入不会无限触发付费摘要。

现有源码已移除旧的滚动截断/微紧凑层，以维持提示词前缀稳定；本项不重新引入逐轮篡改旧消息，也不按 L1/L2/L3 名称机械复制 FirstCoder。

### 10.5 FC-04：不可逆截断前保存原始工具输出，再按需检索

**FirstCoder 机制**：[ToolResultArchive](../../FirstCoder/firstcoder/context/archive.py) 保存原始工具输出与完整性信息；[create_retrieve_archive_tool()](../../FirstCoder/firstcoder/tools/retrieve_archive.py) 按 Session 限定访问，支持关键词附近行窗口、有界浏览和内容取回，返回匹配数量与截断提示。

**本项目接入位置**：[ToolResult.serialize()](../src/my_agent_core/tools/core.py)、[工具结果处理](../src/my_agent_core/loop.py)、[ContextSessionBridge 结果目录](../src/my_agent_core/context.py)、[BackgroundRunner](../src/my_agent_core/background.py)。已有结果落盘继续复用，但不能声称事后落盘可以恢复早先已经丢弃的文本。

实施步骤：

1. 在序列化截断前增加可选的结果处理接口，由 Agent 装配 Session 作用域的归档服务；ToolResult 本身不直接 import Session。
2. 原始文本保存后，模型工具消息只含有界摘要、archive_id、原始大小和检索提示。Bash/后台若更早截断，也需在对应入口先保存输出。
3. 新增普通工具，例如 `retrieve_tool_output(archive_id, query, offset, limit)`，提供分页或关键词窗口，不能暴露任意宿主路径读取。
4. 归档 ID 映射属于当前 Session，校验越界、未知 ID、损坏和输出额度。多模态内容采用单独策略，首版先覆盖文本。
5. 新取回的内容需至少有一次正常进入模型输入的机会，避免刚取回就再次压成相同占位符；复用最近尾部保留规则或增加消费标记。
6. 对长期后台日志，持续排空 stdout/stderr 并限量写盘；`communicate()` 后再截取不能限制收集期间的内存。日志保留期限、容量和清理另设配置。

目标链：`原始结果 → 归档 → 有界序列化 → 模型发现线索 → 检索原文`。

验收：超长测试输出尾部的失败信息仍可检索；跨 Session ID 被拒绝；分页不重复失控；损坏可诊断；既有短输出不额外膨胀提示词。

### 10.6 FC-05：相同工具调用的重复失败检测

**FirstCoder 机制**。[StagnationGuard](../../FirstCoder/firstcoder/agent/stagnation.py) 用工具名、规范化参数和失败信息识别重复。第二次相同失败警告，第三次预告拦截，第四次原样调用在执行前被拒绝。本地版本默认在 benchmark 模式启用。见 [运行模式配置](../../FirstCoder/firstcoder/agent/runtime_capabilities.py#L33)。

**本项目实现**。检测位于 [原生 `edit` 工具](../src/my_coding_agent/tools/edit.py)，在读取当前文件后、计算修改前检查。状态按运行信号隔离，仅保留该次运行最近的 128 个失败记录。

1. 仅统计原文找不到与原文匹配多处，分别返回 `old_text_not_found` 和 `old_text_ambiguous`。审批拒绝、预览过期和 I/O 失败沿各自路径回传。
2. 用目标路径、实际读取的文件字节摘要与有序编辑参数摘要识别重复。同一文件的内容变了，或者参数变了，可以重新尝试。
3. 第 2、3 次失败提供针对性的恢复指引。第 4 次原样调用返回 `repeated_edit_failure`，当前运行可以继续读取文件、换参数或尝试其他工具。
4. 错误作为原有 `ToolResult(ok=False)` 回到模型。修正参数并生成候选修改后，继续走写前 diff、批准和写入前快照核对。

验收覆盖第 4 次拦截、同参数在新文件版本上生效、新运行重新计数、审批拒绝不计入，以及修正参数后仍需批准。参见 [工具测试](../tests/coding/test_edit_tool.py) 和 [Agent 测试](../tests/coding/test_agent.py)。

### 10.7 FC-06：运行预算、实际请求计数与可追踪停止原因

本轮落地请求统计。切换模型时同时更新对话与摘要的模型路由及上下文预算。交互端 `/last-run` 和 headless `metrics.json` 记录对话、Agent 重试和摘要调用，并标注已观测到的 HTTP 尝试和 SDK 重试。运行额度仍为本节候选。

**FirstCoder 机制**：[AgentLoopLimits](../../FirstCoder/firstcoder/agent/loop_limits.py) 分别限制工具轮数、Provider 请求次数、单轮时间；[AgentTurnTelemetry](../../FirstCoder/firstcoder/agent/telemetry.py) 记录请求、重试、工具结果和耗时，主循环在对应边界检查并保存停止原因。

**本项目接入位置**：[Agent](../src/my_agent_core/agent.py)、[Loop 及重试入口](../src/my_agent_core/loop.py)、[摘要请求](../src/my_agent_core/context.py)、[headless 记录](../src/my_coding_agent/headless.py)。保留既有取消控制，新预算对象建议名为 RunBudget，不另建业务工作流。

实施步骤：

1. Agent 创建每次运行的预算对象，在模型请求、工具批次开始前检查；时间使用单调时钟。
2. 区分主循环迭代、实际模型请求、请求重试和摘要请求。BeforeModelCallHook.iteration 不能代表全部请求；需要在真实请求发起点记账。
3. 边界检查防止继续开新工作；正在等待的模型和工具还需要实际超时及现有取消清理。超时必须关闭事件生成器、收敛任务和相关子进程，不只设置状态。
4. 给 AgentEnd 提供明确预算停止原因，保存计数、耗时和已知 usage；区分失败、取消、预算耗尽与自然完成。
5. 父子代理预算明确共享或分配方式。首版先限父运行和单子任务，未实现统一账户前不宣称整个委派树已有总额度。
6. 作为相关增强，借鉴 [build_context_budget()](../../FirstCoder/firstcoder/context/token_budget.py) 对 system、工具 Schema 和输出预留的分项计算；保留我们现有 usage 锚定估算，避免重复计入 Schema 或简单换成字符数除四。

验收：可控假模型无限提出工具时按预算停止，未留悬空 tool_call；重试/摘要计数明确；长请求时间到后真正清理；已发生消息持久化；评估日志不把预算停止记作自然成功。不预先宣称完整计费，未报告 usage 的请求单列。

### 10.8 FC-07：写前预览、批准内容绑定与执行前快照检查

**FirstCoder 机制**：[build_prewrite_review()、PrewriteReview.is_current()](../../FirstCoder/firstcoder/tools/review.py) 保存旧/新内容摘要、unified diff、增删统计和相关路径快照；[ToolExecutor](../../FirstCoder/firstcoder/agent/tool_execution.py) 配合权限流程处理预览、拒绝和过期。这里借鉴预览与版本绑定，不把它称为文件系统事务。

**本项目接入位置**：[permissions.py](../src/my_coding_agent/permissions.py)、[edit.py](../src/my_coding_agent/tools/edit.py)、[write.py](../src/my_coding_agent/tools/write.py)、[FileMutationQueue](../src/my_coding_agent/mutation_queue.py)、RPC/TUI 的权限展示。当前 edit 已有执行后的 diff，本项补的是执行前审查。

实施步骤：

1. 抽取共享的纯计划函数：旧文件、参数 → 新内容、旧哈希、diff、统计。预览与实际写入使用同一计划计算，保持换行/BOM 等现有语义。
2. PermissionRequest 展示计划，批准绑定计划版本及参数；不只是批准工具名字。未创建文件需记录“原先不存在”。
3. 真正执行时获取已有文件锁，在锁内重新读取并核对哈希及参数；一致才写入，不一致返回 `preview_stale`，重新预览。
4. 不能只在 ToolCallHook 里验一次：批次预审和实际执行之间有时间间隔。可使用私有 tool_call_id 计划表或工具包装器传递可信批准，不能把内部 token 当模型可伪造参数。
5. 组合权限策略遵守现有 Hook 短路语义；计算预览失败时返回明确拒绝，不把异常交给通用吞异常机制后继续写。
6. 先覆盖 write/edit；不承诺从任意 Bash 命令预计算修改影响，也不因为有文件锁就宣称外部程序不能竞争写入。

目标链：`计算计划 → 展示 diff → 批准 → 获取文件锁 → 核对快照 → 写入计划内容`。

验收：批准后文件变化或新文件已被创建时不覆盖；同批两项修改使后项预览过期时明确反馈；拒绝无写入；预览结果与实际 diff 一致；不同文件的现有并发能力不回归。

实施步骤：

1. 产品层保存全量目录：server、远程名、对外名、描述、Schema、调用包装器。先增加稳定服务器命名空间，避免两个服务的同名 search 互相覆盖；明确旧工具名兼容。

6. 搜索不改变读写权限或并发声明，未知副作用的 MCP 工具仍按当前保守规则执行。

验收：百项目录初始不携带百份 Schema；搜索命中后下一请求包含对应 Schema；重名不覆盖；无匹配给出改写查询建议；重连和新运行不继承过期激活集合。搜索收益、漏召回与额外一次模型往返按真实任务评估。

验收：只读审查在后台时父 Agent 可做独立任务；有依赖时可明确等待；通知先于/晚于主线结束均有确定处理；相同 tool_call_id 只产生一次工具结果；取消及切会话无错误接续；资源上限生效。

### 10.11 FC-10：产品层 worktree 隔离与子工具重新装配

**FirstCoder 机制**：[WorktreeManager](../../FirstCoder/firstcoder/agent/worktree.py) 创建独立 Git 工作区、计算 diff 并管理清理；[SubagentRunner._run_isolated()](../../FirstCoder/firstcoder/agent/subagent.py) 在 worktree 下重建子 Session 和工具，返回路径、分支、变更摘要，保留产物供父侧审查，不自动合并。

**本项目接入位置**：[SubagentTaskManager._run()](../src/my_agent_core/subagent_tasks.py)、[CodingAgent](../src/my_coding_agent/agent.py)、[build_coding_tools()](../src/my_coding_agent/tools/__init__.py)。核心只增加可注入的子 Agent/工具工厂协议；Git 与工作区重建位于产品层。

实施步骤：

1. 新增产品层 worktree 服务，验证仓库与基线，为每个编码委派创建唯一工作区和分支；不对现有工作区执行 reset/stash 清理。
2. 首版遇到未提交修改明确拒绝该隔离路径，或要求调用方提供已确定的快照方案；不能默默从 HEAD 创建子副本却声称包含父当前修改。

4. 返回基线 commit、分支、路径、已跟踪和未跟踪文件变化、执行结果与日志。普通 git diff 不含未跟踪文件，不能遗漏它们。
5. 不自动合并；父侧先查看结果。失败或有修改时保留 worktree，清理由显式操作完成；记录残留产物，避免任务结束顺手删掉用户可审查内容。
6. worktree 是工作区隔离，不是安全沙箱；Bash 绝对路径、外部 MCP 和共享配置仍有独立访问边界。子代理默认禁用或明确装配这些资源，不能宣称任意工具绝不访问父目录。

验收：两个编码子代理各改自己的同名文件，父工作区无改动；子工具路径都指向各自 worktree；脏基线不被静默忽略；未跟踪文件计入结果；失败不丢补丁；核心包不新增对 Git 产品实现的依赖。

### 10.12 实施顺序、验证方式与暂不移植内容

建议顺序：`FC-01 → FC-02 → FC-03 → 工具失败规范化与 FC-05 → FC-06 → FC-04 → FC-07 → FC-08 → FC-09 → FC-10`。预算、状态与清理先于后台并发；只读后台先于编码后台；审批绑定真实修改先于扩大并发写入范围。

验证先使用现有 tests/core、tests/coding、tests/llm 的假模型与受控子进程，针对失败回滚、消息配对、Hook 短路、取消竞态和路径绑定增加必要回归。随后分别用技能选择、依赖未就绪、重复 edit 失败、超长日志检索、审批期间文件变化、后台审查和隔离修改场景验收。只改文档阶段不声称这些测试已通过。

效果验证固定模型、任务、工具权限与预算，保存成功及失败轨迹，同时观察请求次数、Token、耗时和误拦截。FirstCoder 已有的反馈修复式评测、不同模型和恢复重试结果不能直接证明本项目优化收益。

暂不整体移植以下内容：事件重放式 Session 存储、同步/异步双循环、Textual TUI、完整 planning 包，以及每轮额外模型调用的任务边界分类器。后者先有具体收益与成本证据再评估。保留我们已有 Session 树、事件流、Extension/Hook、长期记忆、文件级写锁与分层边界。

### 10.13 下一步选型：先交付可审查的文件修改

实施状态：FC-07 已在原生 `edit` 和 `write` 接入写前 diff、TUI 审批和写入时的快照复核。下文保留改造前基线和后续候选。实际 RPC 入口和按键见 [桥接协议](coding/05-rpc-bridge-protocol-RPC桥接协议.md)。

本轮按 2026-11-19 的本地源码核对。my-pi-agent 从 `a867a98` 工作区读取，包含未提交改动。FirstCoder 本地 `main` 指向 `3856a10`。10.12 的顺序适合逐一补齐框架模块。以通用 Coding Agent 的实习作品为目标，建议把 **FC-07 提到首个可演示版本**，再用 FC-06、FC-05 和 FC-04 补齐运行与验证能力。依赖升级仍可作为后续演示题材。

现在最明显的差距是审批没有贯通实际入口。RPC 初始化只构造 `PermissionGate(mode=mode)`，没有接确认回调，而门禁在需要询问且缺少回调时会放行。即使手工注入回调，`preview` 也只是写入内容或 edit 参数。现有 `edit` 虽然在运行中计算 diff，但用户要等写入后才能看到。见 [RPC 初始化](../src/my_coding_agent/rpc_server.py#L220)、[权限门禁](../src/my_coding_agent/permissions.py#L45)、[edit](../src/my_coding_agent/tools/edit.py#L164)。

FirstCoder 已把 diff 和文件快照放入批准请求，恢复执行时用 `is_current()` 拒绝过期预览，并有相应回归用例。我们的改进点是让预览和落盘共用一份写入计划，把批准绑定目标路径、原始字节摘要与候选内容，在现有同路径队列内复核，并写入已批准的字节。这样同一运行时通过该队列的重叠修改，也受同一条约束。外部编辑器和其他进程没有共享这把锁，仍可能并发操作。见 [FirstCoder 写前预览](../../FirstCoder/firstcoder/tools/review.py#L55)、[批准后的检查](../../FirstCoder/firstcoder/agent/loop.py#L560)、[过期回归用例](../../FirstCoder/tests/test_agent_context_loop.py#L3830)、[本项目文件修改队列](../src/my_coding_agent/mutation_queue.py)。

**首版设计约束。** 产品层实现审批与提交，通用 Hook 继续承载扩展。需要执行的强制策略由文件工具或专用执行路径校验。等待批准时不持文件锁，响应关联所属运行和唯一请求，只消费一次。拒绝、过期和超时各返回明确的工具结果并闭合原工具调用。源码复用现有 edit 匹配规则、CRLF/BOM 语义与文件队列。首版范围是原生 `edit/write`，任意 Shell 命令的影响不进入这套 diff 承诺。

**首个演示只需要一个小仓库。** 用受控故障让 Agent 给出 `edit`，展示一次批准并运行测试，再展示一次拒绝和一次批准期间文件变化后的过期反馈。用文件字节、Git diff 和 pytest 退出结果核对行为。接线和竞态用假模型与临时目录回归，TUI 另跑一次真实模型确认交互。如果首版做验证报告，采用运行器实际观测的退出结果，模型发出的完成文字只作为说明。FirstCoder 的 [ExecutionEvidence](../../FirstCoder/firstcoder/agent/execution_evidence.py) 可以作为收集证据的参考。

评测分开记录两类数据。交互审查使用同一小任务和人工操作脚本比较变更前后。原生无界面适配器可用于后续验证预算、错误恢复和日志检索，其默认 `autonomous` 模式不覆盖 TUI 审批。真实模型对照固定输入、工作区快照、模型和尝试次数，保存失败记录与判定证据。见 [原生评估说明](../my-pi-eval/NATIVE_EVALUATION.md)。
